# Track B data package

**Setting.** Smart Tech Components is the Smart Tech group's plant in Austria. It machines, checks, assembles and packs the **metal stand-and-frame sets** for Smart Tech TVs. The line has four stations: raw machining (M1), quality check (M2), assembly (M3), packaging (M4). The customers are the group's TV assembly plants and its spare-parts logistics, which order sets shift by shift. One "unit" in all files is one stand-and-frame set.

Starter code: the `machine_sim` repository in the subfolder `machine_sim/` of this folder.

**Time mapping.** 1 tick = 1 minute. 1 shift = 480 ticks (8 hours). All files use this mapping.

| File | Content |
|---|---|
| `demand_profile.csv` | Customer orders for 60 shifts: `shift`, `order_tick` (the orders are placed at the first tick of the shift), `due_tick` (they are due at the end of that shift), `orders` (units). |
| `rate_card.csv` | All cost rates: `category`, `item`, `value`, `unit`, `note`. |
| `failure_rates.csv` | Optional (idea: machine breakdowns): failure modes with probability per part and assumed repair times. |

## How the files fit the simulation

- **Line capacity.** With the default configuration the line delivers about **36.8 good parts per shift** in steady state. M3 (assembly) is the bottleneck at about 100% utilisation. M2 rejects 10% of parts.
- **Demand.** The demand profile is real order data (SupplyGraph, one product) rescaled so that the **average is 85% of the line's capacity** (31.2 orders per shift). Closed days were removed; a few working shifts still have no or very few orders (for example shifts 59 and 60). Order sizes still swing a lot (from 0 up to about 75 units in one shift), so capacity on average is enough, but the swings and a supplier outage will cause backlog and lost sales.
- **Running long scenarios.** The default configuration has `materialStock: 200`, so the line stops after 200 parts (about 5 shifts). For longer runs set `materialStock` to `-1` (infinite stock).
- **Supplier outage.** In the reference scenario the outage is a **halt of the source**: for 960 ticks (2 shifts) starting at tick 4800 no part is released and no material cost is booked. Use it in at least one scenario so that results can be compared. A reorder point, lead time, safety stock or a second supplier are **countermeasures against the outage**. The simulation has no parameter for these supplier-side options, so they are not part of the starter simulation (the rate card rows for them can be used for your own ideas, with clearly stated assumptions). What the helper can test is starting finished-goods stock (an argument of `runHeadless`), buffer capacity, cycle times, reject rate and an **extra machine**: copy the `M3` entry in `config.machines` with a new id (for example `M3b`); machines with the same `stationId` work in parallel. Material is booked at `material_cost_per_part` when a part is released into the line. Emergency replenishment adds `expediting_premium`, parts from a second supplier add `second_supplier_price_premium`.
- **Running scenarios.** The starter repo contains the helper `runHeadless` (`src/headless/run.js`). It runs the engine tick by tick without the UI and applies the order rules below. Call it with `config`, `seed`, `shifts`, `demand` (the `orders` column), an optional `outage: { startTick, endTick }` and `initialFinishedGoods`. It returns:
  - per-shift rows (`produced`, `scrap`, `orders`, `shipped`, `shippedOnTime`, `backlog`, `stock`, `wip`);
  - KPIs (`goodParts`, `released`, `scrap`, `serviceLevel`, `backlogEnd`, `avgWip`, `lineYield`, `finishedGoodsEnd`, utilisation and OEE per machine);
  - an **event log** (machine starved or blocked episodes, outage start and end, per-shift shortfalls). Your advisor reads the KPIs and the event log. The log is noisy (every longer starved or blocked episode of every machine, mostly M4 waiting): **summarise it per machine and shift before you give it to the advisor.** The outage events use the helper's tick numbering (counted from 0, `startTick` included, `endTick` excluded); the machine episodes use the engine's ticks (the first tick is 1).
- **Costs from the helper output.** The helper computes no costs: take released parts (material), good parts, average WIP and finished-goods stock per shift from its output, take the scheduled machine hours as shifts x 8 h per machine (plus any extra machine), and apply the rate card.
- **What the helper does not do.** It passes `seed` to the configuration, but the engine ignores it until you implement seeding, so runs are random until then (use seeds 1 and 2; seed 0 is the helper's default and a falsy check would swallow it). The supplier outage exists only inside the helper (its `outage` option halts the source), not in the engine or the UI. If you add the outage to the engine, use this interface: the engine reads `config.source.outage = { startTick, endTick }`; the helper then writes the outage events from that setting as well. The helper always runs with infinite material (`materialStock` -1), whatever the config says.

## Order and service-level rules

These rules make results comparable between teams. Use them, and state it if you deviate.

- Orders for a shift are placed at `order_tick` and are **due at `due_tick`**. They are served from **finished-goods stock** (good parts that left the line). Start with an empty stock unless a countermeasure says otherwise.
- At each `due_tick` ship as much as the stock allows, oldest orders first. What cannot be shipped stays in the **backlog** and is served as soon as stock is available.
- **Service level** = units shipped on or before their due tick / units ordered.
- A unit that is not shipped by its due tick costs the **lost-sales penalty once**. The sale itself is kept if the unit is delivered later.
- **Sanity check:** with the default line, no finished-goods stock and these rules, the service level over the first 20 shifts of the demand profile (scenario *demand swing*) is about **57%** (about 48% with the reference outage, scenario *both*). With flat demand of 34 per shift it is about 100% (about 76% with the reference outage). The simulation is random in one place only, the reject gate of M2. Until you implement seeding every run differs: over 30 runs the service level varied by about +/-1 point (standard deviation 0.7) and scrap by about +/-10 parts (standard deviation about 9 of about 83). Because the demand is fixed and M3 is the bottleneck, a seed mainly changes scrap and the number of parts released, and only slightly the good parts. Do not expect large differences between seeds; for flat demand plus the reference outage the service level varies more (standard deviation about 3 points). Differences of only about 0.1 good parts per shift between two runs are noise. Because old orders are served first, one bad day delays the following days too. Your numbers should be in this range.

## Scenario conventions

**Checking an outage in the engine.** The helper's own `outage` option is the reference: with the same configuration and the same seed, an engine implementation of the reference outage must give the same per-shift rows as `runHeadless` with `outage: { startTick: 4800, endTick: 5760 }`. Before you have seeding, compare averages over many runs instead. The outage starts at the first tick of shift 11.

- **The four reference scenarios:** *baseline* = **flat demand of 34 orders per shift** (about 92% of the line's capacity), no outage. *Supplier outage* = flat demand plus the reference outage. *Demand swing* = the real `demand_profile.csv` (first 20 shifts), no outage. *Both* = the demand profile plus the reference outage. Reference service levels without any countermeasure (empty stock, 30 runs): baseline about **100%**, supplier outage about **76%**, demand swing about **57%**, both about **48%**.

- **Horizon:** every scenario runs for **20 shifts** (the first 20 rows of `demand_profile.csv`; the remaining 40 are spare for your own tests).
- **Results table:** show **every scenario twice**: without and with your recommended countermeasure. Where a scenario has no verified countermeasure, the two rows are identical. If you add features to the simulation, add your own scenarios as extras and keep the four reference scenarios unchanged so that results stay comparable.
- **Work-in-progress (WIP):** WIP is **reported with every run and every verification, but it is not a pass/fail criterion** for the advisor. Its cost is already inside the holding cost of the cost model, so a proposal that raises WIP pays for it there. WIP moves with the line: more good parts per shift, a lower reject rate, a shorter source interval or bigger buffers raise it (by roughly 10% to 45% depending on the scenario), while a faster bottleneck can lower it a lot (with M3 at 12 ticks WIP falls from about 13 to about 3), because the parts that queued in front of M3 now pass and the line is limited by the source instead. Both are effects of the line, not bugs.
- **Total profit** of a scenario = revenue (units shipped x selling price) - machine cost - material cost - holding cost (WIP and finished goods) - amortised one-time costs - lost-sales penalty - value of the starting finished-goods stock + value of the finished goods left at the end (both at the baseline cost per good unit, see below). Every comparison between options must include the lost-sales penalty.
- **One-time costs** (`second_supplier_qualification`, `extra_buffer_slot`, `parallel_machine_investment`, `cycle_time_reduction_investment`, `reject_rate_reduction_investment`) are amortised over 8 years at 240 shifts per year, which is 1,920 shifts. A 20-shift scenario carries 20/1,920 of the amount. `parallel_machine_depreciation_per_shift` is the **same cost** as the amortised investment (95,000 / 1,920 = 49.48 per shift): use one of the two, not both. The extra machine also accrues its station's machine hour rate for every scheduled hour.
- **Finished-goods stock is valued at EUR 103 per unit (the baseline cost per good unit of EUR 102.8, rounded).** Starting stock (a countermeasure) is charged at that value at the start of the run, and all finished goods left at the end of the run are credited at that value, so stock costs only its holding cost `holding_cost_finished_goods` (per scheduled hour, 8 per shift). Stock is shipped first-in, first-out. `perShift.stock` is the stock after shipping: the average stock of shift s is the stock at the end of shift s-1 (the initial stock for shift 1) plus half of the production of shift s. The advisor does not price its proposals; the business side does.
- **Extra machine at M3:** it costs its station's machine hour rate for every scheduled hour (EUR 720 per shift) plus EUR 49.48 depreciation per shift; the hour rate already includes capital cost.
- **OEE** of a machine = availability x performance x quality, taken from the engine's state counters over all scheduled ticks. Availability = 1 (the starter simulation has no breakdowns; if you add them, availability falls below 1). Performance = processing ticks / (processing ticks + blocked ticks + starved ticks). Quality = good parts / parts processed (only M2 rejects). `runHeadless` returns all three per machine. Report OEE **per machine**. M1, M2 and M4 show low values (about 35%, 25% and 15%) because they are blocked or starved by the bottleneck M3: that is the effect of the line, not a bug. Because M3 is the bottleneck and sits after the quality gate, its OEE is close to 100% without an outage (about 91% with the reference outage, while it starves) and says little about the line, so also report the **line yield** = good parts / released parts (about 88% for the default line: M2 rejects 10% of the parts it processes and some released parts are still in process at the end, so scrap is about 10% of the released parts).

## Cost conventions (see `rate_card.csv`)

- Machine cost accrues for **every scheduled hour**, not only while a machine processes. That is why utilisation matters for cost.
- Cost per good unit = (machine cost + material of all released parts + holding cost) / good units. Scrap is already inside this total. For a scenario with a countermeasure add the amortised one-time costs (stock value is neutral, only its holding cost counts).
- **Improving a machine costs money.** A shorter cycle time or a lower reject rate is not free: the rate card prices them as one-time investments (`cycle_time_reduction_investment` per tick of cycle time removed from one machine, `reject_rate_reduction_investment` per percentage point of reject rate removed). They are amortised like the other one-time costs. These two rows are **organiser assumptions** for this exercise: you may challenge them in your business case, but a comparison must use some price. The source interval (release rate) has no investment price: its cost shows up as material and holding cost.
- Lost sales: each ordered unit that is not shipped by its due tick costs `lost_sales_penalty` (see the order rules above).
- **Baseline check** (default configuration, 20 shifts from an empty line, empty finished-goods stock): **EUR 102.8 per good unit** = machine cost + material of all released parts + holding cost of the parts in the line, divided by good units, with no amortised one-time costs and no finished-goods holding. The selling price is EUR 180 (contribution about EUR 77 per unit). Your own baseline should land close to this (a warmed-up line is about one euro cheaper). If you also charge holding for the finished goods that pile up during the 20 shifts, the cost is a few euros higher: compare like with like and explain the difference.
